# Bridge reliability, wave 1: work items

The exact specification each wave-1 work item was implemented from (2026-09-18), so that any agent can finish or redo an item from the repository alone. Plan sections refer to [2026-09-18-bridge-reliability.md](2026-09-18-bridge-reliability.md); evidence is in [2026-09-18-bridge-reliability-evidence.json](2026-09-18-bridge-reliability-evidence.json).

Each item: branch from the release base, implement with regression tests, run the full suites with an isolated short HOME/TMPDIR, then three independent reviews (correctness against the plan; behaviour at the boundaries with Codex, ChatGPT and the launcher, including concurrency and restarts; an adversarial tester), fix confirmed findings, and integrate all items into one branch that passes `bun run verify` and the updater's build path.

Include the table-driven contract test that copies Codex 0.154 is_retryable / try_parse_retry_after semantics, an SSE snapshot of the response.failed frame, and the "did not confirm" replay test.

## gate (`fork/rel-admission-gate`)

Implement plan sections 1.3 "Гигиена cooldown", 2.1 "Шлюз допуска" and 2.2 "Блокировка тяжёлых фаз" (new src/adapters/chatgpt-web/rate-limit-gate.ts; browser-worker.ts ChatGptRateLimitCooldown, forProvider, escalate, run/assertReady -> awaitReady(signal); index.ts runTurn; concurrency.ts; turn-execution.ts; retry-policy.ts). Escalation per incident not per failed parallel turn; state keyed by account/profile persisted atomically to ~/.codex-chatgpt-web/state/chatgpt-rate-limit.json via the configured home (tests use a temp home), until capped at now+300 s, corrupt file ignored; a local cooldown refusal never spends the retry budget; during cooldown a turn WAITS inside the bridge with heartbeats (reuse the existing heartbeat mechanism; keep Codex stream idle timeouts in mind) and a visible reasoning-summary line; after cooldown one probe, others released only after the probe is accepted, at least 10 s apart; at least 3 s between Temporary Chat openings; concurrency cap 5 before an incident, 1 after, +1 per clean completion; beyond the cap a FIFO queue instead of an error; compaction and its fallback go through the same gate; a turn waiting for Codex tool results does not hold a send slot; waiting more than 15 min or 3 incidents in 30 min -> terminal invalid_prompt with the time and one action. Use fake clocks in tests; include the regression "three waiting turns do not start in the same second" (17:34:23-36) and deadlock tests (retained tab owner, tool-result waits, cancellation while queued releases the slot).
